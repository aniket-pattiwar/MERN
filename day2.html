Lab: Aggregation Pipeline

The aggregation pipeline is a powerful framework for data analysis. It processes documents through a series of stages.

Stage Purpose SQL Equivalent Example
$match Filters documents, similar to a find() query. WHERE { status: "Active" }
$group Groups documents by a specified key to perform aggregate calculations (e.g., sum, average). GROUP BY { _id: "$dept", total: { $sum: 1 } }
$sort Sorts the documents based on a specified field. ORDER BY { age: -1 }
$limit Limits the number of documents passed to the next stage. LIMIT 5 (Top 5 results)
$unwind Splits array values into separate documents. LATERAL VIEW / CROSS JOIN "$tags"
$project Selects, renames, or removes fields in the output. SELECT { username: "$name", age: 1, _id: 0 }
$lookup Adds matching data from another collection. LEFT OUTER JOIN { from: "orders", as: "products" }

The Importance of Sequence

The power of the pipeline comes from chaining stages together. The order matters! The output of one stage becomes the input for the next. For performance, it's almost always better to filter first with $match to reduce the number of documents processed by later stages.

Recommended Sequence (Best Performance)
1. $match
Filter Early
→
2. $sort/$limit
Reduce Size
→
3. $lookup
Join Data
→
4. $project
Reshape
Sequences to Avoid (Performance Killers)
  • $unwind before $match
  • $lookup before $match
  • $group before $match

Lab: Storing Files with GridFS

GridFS is a specification for storing and retrieving files that exceed the BSON-document size limit of 16 MB. It divides a file into smaller chunks and stores each chunk as a separate document.

Why do we need this?
Storage Formats
Files < 16MB (Standard)

Stored as a single field inside a document using BinData.

  "name": "avatar.png",

1 Document = 1 File

Replication (High Availability)

Replication means keeping the same data on multiple MongoDB servers. This group is called a replica set. If one server fails, another one can take over, so your app stays online.

Sharding (Scalability)

Sharding splits a big collection so different servers each own a slice of the data. MongoDB can then handle more users, more writes, and more records without one server becoming a bottleneck.

Image 1: Cluster Layout
Image 2: Data Flow
Detail Explanation Why It Matters
Application & mongos router The app talks to a router named mongos instead of directly to servers. One router keeps traffic organized and sends each query to the right shard.
Shards (Shard A, B, C) Each shard stores part of the dataset (e.g., customers starting with A-G). Distributes load so no single server is overwhelmed.
Config servers Hold a map of which shard owns which range of data. Mongos uses that map to read/write without guessing.

Easy phrasing: Sharding lets many servers share the work while mongos keeps the traffic going to the right place.
Need Single Server Sharded Deployment
Data size Fits comfortably within a single machine (e.g., < 100 GB). Too large for one disk or memory; grows rapidly.
Write throughput Moderate writes (hundreds/sec). High writes (thousands/sec) across diverse keys.
Operational cost Cheaper to maintain. Higher ops cost but required for scale.
